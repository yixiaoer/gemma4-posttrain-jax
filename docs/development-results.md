# 实验结果与分析

实验围绕三个问题展开：模型和训练目标是否正确，训练是否改善了任务表现，以及 TPU 上的时间和内存花在了哪里。下面把每个实验的配置、结果和解释放在一起。词表并行、采样精度和权重同步三个专题还展开了定位问题的过程，并提供独立实验入口。多数性能与学习结果来自之前的固定版本；最新的保存和恢复测试单独注明日期。

文中一个训练步包括计算 loss、求梯度，以及由 Adam 修改一次模型参数。B 表示每批题目数，G 表示每题回答数，P/N 表示 prompt 宽度和最多生成的 token 数，micro 表示训练 microbatch，μ 表示同一批生成数据用于几个训练步。SFT 的 T 表示序列长度。例如 B8/G8/micro4 意味着生成 64 条回答，每次梯度计算处理 4 条，累积完成后再修改模型参数。

## 模型和梯度的正确性

本项目与 Hugging Face Transformers 使用相同来源的 E2B 权重和输入进行比较。模型支持文本前向、PLE、共享 KV、滑窗 attention 和 layer scalar；视觉、音频及所有 Gemma 4 变体尚未覆盖。

| 比较设置 | 结果 |
|---|---|
| 真实 E2B，双方 CPU FP32 | 末位 logits 最大绝对误差约 `4.96e-5`，13 个 greedy token 一致 |
| 真实 E2B，TPU BF16 与 Transformers CPU FP32 | 普通文本和聊天输入各 13 个 greedy token 一致 |
| 小模型梯度，双方 CPU FP32 | 全梯度相对 L2 误差约 `1.000e-5`，最差参数数组约 `1.924e-5`，均低于 `1e-4` |

这些固定短输入验证了模型公式和权重映射的主要路径。较长生成仍可能因微小概率差异逐渐分叉，因此还需要单独检查缓存、停止条件和生成过程中记录的概率。

## 大词表计算为什么曾经很慢

训练需要目标 token 的 logprob。直接计算完整 `[B,T,V]` logits 会占用大量内存，因此先沿词表分块计算。但真实 E2B 的训练步仍然很慢：减少了中间 logits，并没有自动消除权重通信。

### 从训练耗时定位到输出头

首先需要区分 attention、输出头的矩阵乘和设备通信，不能仅凭模型结构决定改哪个 kernel。沿实际训练图检查后，发现输出头附近出现了整张 embedding 大小的 all-gather。下面是数值对照中一条真实 HLO 指令的关键部分，省略了布局与后端配置：

```text
%all-gather.1268 = bf16[32,8192,1536] all-gather(...)
```

这里没有直接出现词表维度 `262144`，因为它被拆成了 `32×8192`。按元素数计算，输出仍是 `262144×1536×2` 字节，即 768 MiB；只搜索形状里有没有完整词表数字，会漏掉它。这个大小是指令输出大小，不能直接当作通信链路上传输的总字节数。

接下来只改变 logprob 的分片方式：保持模型、输入和优化器配置，比较自动分片与显式词表并行。显式实现让 embedding 按词表留在各设备上，复制较小的 hidden 和目标 token，最后合并归一化结果。设设备 d 上的局部最大值和指数和为 m_d、s_d，则：

```text
m = max_d(m_d)
log Z = m + log(sum_d(s_d * exp(m_d - m)))
log p(target) = target_logit - log Z
```

实现时还遇到两个具体问题：`scan` 的初始状态需要声明为随设备变化；JAX 当时没有 `pmax` 的反向规则。最大值只是数值稳定用的平移量，相关导数会在公式中抵消，因此代码在输入侧写成 `pmax(stop_gradient(local_max))`。把 `stop_gradient` 放在 `pmax` 外面仍会在求导时失败。对应实现是 [losses.py](../gemma4_posttrain_jax/losses.py) 的 `_vocab_parallel_logps`。

这个改动在真实模型的数值对照图中消除了两次完整 embedding all-gather。还需要独立检查 loss、梯度和完整 Adam 训练步耗时：通信减少本身不能证明数值正确，也不能给出整步收益。

### 真实模型的验证结果

TPU v4、E2B、B8/T1024、BF16 计算、FP32 主参数和 Adam、关闭重计算，每组预热后测量五次，得到以下均值：

| 训练范围 | 自动分片 | 显式词表并行 | 速度比 |
|---|---:|---:|---:|
| 冻结 embedding | 9038.304 ms/步 | 314.339 ms/步 | 28.753 倍 |
| 训练全部文本参数 | 9201.462 ms/步 | 405.784 ms/步 | 22.676 倍 |

数值检查使用较短的 B8/T128 输入，比较了 540 个参数数组的梯度：loss 差为 0，全梯度相对 L2 误差为 `0.00396193245`，余弦相似度为 `0.99999219665`。最差单个数组的相对 L2 误差约 `0.02354`；这次 BF16 实验采用的是全梯度 `1e-2` 阈值，并没有要求所有数组都低于它。

这组速度提升来自特定配置中的输出头通信瓶颈。它说明优化应从实际计算图和 profile 出发，而不能仅凭模型属于 Transformer，就决定先改 attention。换用其他形状、重计算方式或编译器版本后，需要重新测量。

### 运行词表并行对照实验

[probe_vocab_logprob.py](../scripts/probe_vocab_logprob.py) 使用小型合成输入，比较 dense 参考、自动分片和显式词表并行，检查 embedding 与 hidden 的梯度，并列出实际 HLO 中的 all-gather。它可以在四个 CPU 虚拟设备上运行：

```bash
JAX_PLATFORMS=cpu XLA_FLAGS=--xla_force_host_platform_device_count=4 \
  .venv/bin/python scripts/probe_vocab_logprob.py --backend cpu \
  --save-ir --output-dir outputs/vocab-cpu
```

本次 CPU 运行中，自动分片有两条完整 embedding 大小的 all-gather，显式词表并行为零；两种实现相对 dense 参考的梯度误差均小于 `3.2e-7`。该实验用于观察分片方式对计算图的影响；完整模型的 TPU 训练速度仍需单独测量。在现有四芯片 TPU 环境中可改用 `--backend tpu`，不设置 CPU 环境变量；新的设备结果应单独记录。

### 与 MaxText 的计算对照

固定 MaxText 0.2.4 Linen、真实 E2B、四芯片、B4/T512、全 FP32，执行前向、反向并返回梯度：本项目稳态均值为 568.460 ms，MaxText 为 826.377 ms，时间比约 1.454。相同配置下 MaxText 的完整 AdamW 步骤发生 HBM OOM，因此这组结果只比较前向与反向计算。

包含 Adam 和 donation 的完整训练图，有时反而比返回全部梯度的图更快。输出需要保留多久、哪些缓冲区可以复用，以及算子能否融合，都会影响实际速度；验证和计时应尽量使用同一张训练图。

## 采样概率的数值误差与开销

这项问题是在增加 Top-p 后暴露的：CPU 数值检查通过，TPU 上记录的 raw logprob 却超出了原来的误差要求。首先要分清，是过滤分布改变了、抽到了不同 token，还是同一 token 的全词表概率算得不够准。

调查按以下顺序缩小范围：

1. 关闭 Top-p，保持 logits、随机 key、温度和 TopK 不变。旧函数和增加过滤分支后的对照仍一致，说明仅添加分支不能解释偏差。
2. 移除模型、KV cache 和训练，只把固定 logits 输入采样函数。用 NumPy FP64 计算完整词表的归一化，再取实际选中 token 的概率。这里比较的是 raw policy logprob；温度和截断后的 proposal 概率是另一项量。
3. 保留原采样选择，比较默认 `log_softmax` 与显式高精度 `exp/log`。矩阵乘精度设置不能代替这些原语的精度要求。
4. 同时看数值输出和优化后的 HLO。源码写了精度参数，只证明发出了请求；编译结果仍保留精度属性，才能说明要求进入了这次可执行图。

固定词表大小 97 和 262144，分别运行 greedy、温度 1 的完整词表采样、温度 0.8 的 TopK=7 采样。CPU、TPU 共 12 个对照，得到：

| TPU 词表大小 | 旧归一化的最大误差 | 高精度 exp/log 的最大误差 |
|---|---:|---:|
| 97 | `6.7746e-5` | `2.7686e-7` |
| 262144 | `6.5304e-5` | `2.1565e-7` |

这些输入上选择的 token 没有变化，部分概率值发生了变化。TPU 的 greedy 小词表图包含以下两条指令，省略了布局和 metadata：

```text
%exp.0 = f32[8,97] exponential(%sub.2), result_accuracy={mode=highest}
%log.0 = f32[8] log(%exponential_reduce_fusion), result_accuracy={mode=highest}
```

它们支持“归一化精度要求进入了编译结果”这个判断，不能单独证明所有输入的误差上界，也不能证明训练曲线保持不变。随机采样自身还包含其他数学运算，这次没有把它们全部改成高精度。

### 运行采样精度对照实验

[probe_sampling_math.py](../scripts/probe_sampling_math.py) 生成固定 logits，分别调用旧版和当前采样器，再将所选 token 的 logprob 与 NumPy FP64 参考值比较：

```bash
JAX_PLATFORMS=cpu .venv/bin/python scripts/probe_sampling_math.py \
  --backend cpu --save-ir --output-dir outputs/sampling-cpu

# 在已有 TPU 环境执行，输出放到另一个目录。
JAX_PLATFORMS=tpu .venv/bin/python scripts/probe_sampling_math.py \
  --backend tpu --save-ir --output-dir outputs/sampling-tpu
```

脚本使用 NumPy 随机种子 20260912 生成输入，使用 JAX 随机种子 123 采样。每次运行将配置、软件版本、所选 token、logprob 和误差写入 `summary.json`；`--save-ir` 额外导出编译图。2026-09-13 已在 macOS CPU 上运行六个配置；上表的 TPU 数字来自 2026-09-12 的实验，使用 JAX/jaxlib 0.11.1 和 libtpu 0.0.46。

另一次 B32、262144 词表的合成输入实验，在预热后交替执行旧版和高精度归一化，各测十次，得到以下中位数：

| 采样设置 | 旧归一化 | 高精度归一化 |
|---|---:|---:|
| Greedy | 0.371 ms | 0.440 ms |
| 温度 1，完整词表 | 0.944 ms | 1.001 ms |
| 温度 0.8，TopK=50 | 2.567 ms | 2.634 ms |

这部分增加约 0.06–0.07 ms，只覆盖采样和 logprob 计算。完整词表的 Top-p 排序可能贵得多：同样的 batch 和词表下，温度 0.8、Top-p=0.9 约需 86.25 ms/步；先取 TopK=50 再做 Top-p 约需 2.64 ms/步。这两种设置产生不同的采样分布，选择时需要同时考虑生成行为和开销。

## 监督微调的训练结果

两组较早的 E2B 实验分别检查模型能否记住一组数据，以及真实数据上的训练 loss 是否下降：

| 实验 | 配置 | 结果 |
|---|---|---|
| 单个 batch 过拟合 | 冻结 embedding，B8/T128，100 步 | loss 从 3.644784 降到约 `5.809e-5` |
| GSM8K SFT | B8/T512，200 步 | 前 20 步 loss 均值 0.912670，后 20 步 0.429116，下降约 53.0% |

训练 loss 的变化表明模型可以学习这些样本，泛化表现仍应通过独立评估判断。2026-09-12 的公开示例将一道内置问答重复四份，使用 B4/T128 输入连续训练 4 步，检查参数修改后能否继续训练及复用编译结果。四步的 loss 分别为 5.098011、1.635544、1.139039、0.653751，后续步骤均复用了首次编译的结果。

## GRPO 与其他策略优化设置

一组较长的 E2B 训练使用全部文本参数、BF16 计算和 FP32 状态，B32/G8/P512/N1024/micro8，每批数据用于一个训练步。固定随机种子 0，分别使用 KL 系数 β=0 和 β=0.04，训练 300 步：

| 固定 500 题监测集 | 初始准确率 | 第 300 步准确率 |
|---|---:|---:|
| β=0 | 89.2% | 90.6% |
| β=0.04 | 89.2% | 89.0% |

这份集合在训练中被反复评估，每种设置也只运行了一次；配对置信区间都包含零，因此结果还不足以说明稳定提升或 KL 惩罚有害。

另外比较了 26 组算法设置，每组使用三个不同的随机种子，各训练 30 步。配置为 E2B、全部文本参数、B8/G8/P512/N1024/micro8；多数设置每批数据用于两个训练步，RLOO 每批数据用于一个训练步。不同设置的生成量并不相同，判断效率时需要一起看生成 token 数和耗时。

这期间发现，奖励全为 0.1 的组曾因浮点均值与标准差的舍入误差，产生约 −0.00739 的非零优势。改为先相对组内第一项中心化后，可以避免这类残差被放大。在上面的 β=0 长训练中，9,600 组里只有约 16.23% 包含不同奖励，也说明名义 batch 大小不等于有效的组内学习信号量。

## 在 MATH500 上的强化学习效果

使用 E2B-it，训练全部文本参数，B8/G8/P2048/N2048/micro4，每批数据用于两个训练步，开启重计算，学习率为 `2e-6`，KL 系数为 0。分别使用随机种子 0、1、2 进行了三次训练，每次训练 30 步。训练期间使用的验证集与最终 MATH500 评估集分开。

| 评估模型 | 正确题数 | 准确率 | 相对初始模型：由错变对 / 由对变错 |
|---|---:|---:|---:|
| 初始模型 | 334/500 | 66.8% | — |
| 训练后，随机种子 0 | 401/500 | 80.2% | 79 / 12 |
| 训练后，随机种子 1 | 398/500 | 79.6% | 79 / 15 |
| 训练后，随机种子 2 | 392/500 | 78.4% | 69 / 11 |

三次训练后的平均准确率为 79.4%，比初始模型高 12.6 个百分点；三次结果的样本标准差为 0.9165 个百分点。这个标准差描述不同运行之间的波动，并不是置信区间。结果说明模型在这组数据和预算下有明显改善，能否推广到其他预算、数据和模型，还需要更多实验。

同样形状在关闭重计算时发生 HBM OOM，开启后可以保留原来的题目和长度预算完成训练。这是容量上的改善，不能单独归因于算法。

最终评估使用 HuggingFaceH4/MATH-500 的 500 道题，greedy 解码，prompt 和回答长度上限均为 2048 token。实验使用 JAX/jaxlib 0.11.1、libtpu 0.0.46 和最高矩阵乘精度；评分以数据集提供的标准答案为准。

2026-09-12 已用当前评分代码重新处理全部回答，答案和格式评分均与记录一致。旧实验保存了文本、长度和评分，没有保存实际 token ID。采样精度修改后的版本尚未重新运行这三次训练，因此这里保留的是原实验的学习结果。

## 原生生成与 tpu-inference 的比较

### 离线生成

真实 E2B、四芯片 TPU v4、B32/P512/N256、greedy 的一组早期实验中，原生 JAX 的稳态有效吞吐为 5,384.716 token/s，使用旧 RPA v4 兼容路径的 tpu-inference 为 2,981.353 token/s，后者约为前者的 55.37%。

两边只有 17/32 条完整生成序列一致，软件栈、矩阵精度、输出长度、padding 和执行方式也没有完全对齐。这组数字适合帮助发现需要控制的变量，尚不能作为通用性能排名。

后续分别检查了几类开销：

| 改动 | 实测观察 |
|---|---|
| logprob 容量从 20 降到 1 | 同输出下吞吐约提高 6.54%，每次均生成 8,121 个有效 token |
| 融合窗口从 10 增到 32 | 同输出下吞吐约提高 9.59%，融合调用从 28 次降到 12 次 |
| 缩小请求容量 | 调用从 256 次增到 465 次，出现 209 次单请求尾段 |
| 同步与异步融合对照 | 相邻对照吞吐约提高 1.11%/3.07%，但只有 28/32 条 token 序列一致 |

这些改动分别测量，收益不能直接相加。较小的请求容量可能因路由和入场延迟而更慢；融合窗口影响一次设备调用连续做多少步，异步调度影响主机和设备如何配合。用于 greedy 测速的低 logprob 容量，也不一定适用于需要恢复采样分布的随机训练。

### 固定相同 token 历史后的耗时

为排除回答分叉和长度差异的影响，对照实验让两个后端使用相同的 token 序列。两边均为 JAX/jaxlib 0.11.0、libtpu 0.0.44、DEFAULT 矩阵精度和四芯片 TPU v4，B32/P512/N256，选取相同的 64 个解码步：

| 测量范围 | 时间 |
|---|---:|
| 原生 JAX 设备循环 | 358.084 ms |
| 引擎两个解码 module | 381.209 ms |
| 引擎包含辅助活动的两个完整窗口 | 405.330 ms |

原生 batch 为 32；引擎将请求按 8/7/9/8 分到四个 rank，padding 后形成 64 个槽位。两边仍使用不同的 attention、编译图和 trace 采集方式。设备 module 之外的时间可能包含准备、提交、传输和等待，不能全部归为 CPU 计算。原先的完整吞吐差距仍有一部分需要继续解释。

当前适配器采用 batched RPA、TP1 和同步调度；上述一些实验采用旧 RPA 或额外实验补丁，不应混为同一个实现的默认表现。

## 权重同步的成本

训练和推理可能使用不同的权重类型、布局和参数结构。同步包括转换、传输、内容检查、版本更新和缓存失效；只测一次参数赋值会漏掉许多实际开销。

早期 E2B 四步训练中，冻结 embedding，B2/G4/P512/N256/micro4，每批数据用于一个训练步，开启重计算。原生 JAX 使用四芯片，引擎使用训练两芯片加推理两芯片；动态补采后，两边实际分别生成 120 条/29,750 token 和 112 条/27,782 token，工作量不同。引擎后面三步同步累计 213.301 秒，占不含保存的总步时约 81.28%。

### 如何排除“主要慢在传输”这个解释

同步总时间同时包含源数据读回、FP32 有限性检查、BF16 转换、布局整理、目标传输、目标读回检查和状态刷新。先分别计时，才发现 BF16 有限性扫描和目标相等比较值得单独检查。随后把设备和引擎移除，用 2048×8192 的 BF16 数组进行 CPU 对照实验：每个数组 32 MiB，分别比较 C/C 和 F/C 布局。

旧主机上的 C/C 数值相等检查中位数约为 24.038 ms，按 uint16 位模式比较约为 4.216 ms；F/C 则约为 208.968 ms 和 145.642 ms。后者仍然很慢，说明跨布局访问的成本没有被位检查消除。

这个候选不能只看速度。BF16 指数域全为 1 时才属于 Inf/NaN，因此可以用 `(bits & 0x7F80) != 0x7F80` 检查有限性。实验枚举了全部 65,536 种编码，与 NumPy 判定逐项比较。位相等还要求正负零保持一致，比数值相等更严格；相同 NaN 位模式却会通过位比较，所以它不能替代有限性检查。对应产品函数是 [inference_weights.py](../gemma4_posttrain_jax/inference_weights.py) 的 `bf16_finite` 和 `bf16_bits_equal`。

还要防止主机缓存造成假加速：先前 `device_get` 过的 JAX 数组可能已有主机副本。历史设备对照每次用 `device_put(..., may_alias=False)` 创建独立设备副本并等待完成，检查计时前没有主机缓存；副本准备单独计时，然后按 A/B/B/A 交错同步，最后检查源 FP32 参数、全部 BF16 目标和生成结果。这个不含 Adam 的实验中，同步中位数从约 60.084 秒降到 37.852 秒；它仍需下面的真实训练对照来检验。

### 完整训练中的同步耗时

随后在完整训练中比较两种实现，只替换了两处 BF16 主机检查：有限性扫描和目标数组的相等比较。使用 BF16 位模式检查可以减少数值转换开销，同时保留完整传输、FP32 源数据检查和目标内容读回。两种实现各运行四步，排除第一步和编译、初始化后，第 2–4 步累计耗时为：

| 测量范围 | 原数值检查 | 位模式检查 | 耗时减少 |
|---|---:|---:|---:|
| 布局转换与权重同步 | 171.571 秒 | 116.055 秒 | 32.357% |
| 训练步，不含保存 | 204.812 秒 | 149.311 秒 | 27.099% |
| 保存状态 | 25.645 秒 | 25.526 秒 | 单独计时 |

比较覆盖 14 批生成、112 行文本和奖励、四步参数变化、四版 BF16 权重，以及最终 1,548 个状态数组，结果一致。主要节省的是 CPU 检查时间，没有通过少传数据或省略目标内容验证来加速。两种实现各只有一次四步运行，还需要重复、交错测量才能判断收益是否稳定。

### 运行 BF16 权重检查实验

[probe_weight_checks.py](../scripts/probe_weight_checks.py) 会枚举全部 BF16 编码，检查正负零、NaN、单 bit 改变和 C/F 布局，再按 A/B/B/A 交错测量两种实现：

```bash
.venv/bin/python scripts/probe_weight_checks.py \
  --output-dir outputs/weight-checks
```

脚本直接调用权重同步模块中的检查函数，只需核心依赖。2026-09-13 已在 macOS 上完成上述测试，覆盖检查行为和 CPU 耗时；完整 TPU 权重同步仍需单独测量。不同 CPU、NumPy 版本和布局的时间不应混入历史训练对比。

## 保存和恢复的实际测试

2026-09-12，当前原生 E2B 示例完成了连续四步训练、第 2 步保存、新进程恢复到第 4 步，以及两份末步模型的独立评估。配置为 B2/G4/P512/N256/micro4，冻结 embedding，开启重计算，学习率 `1e-6`。

三个完整状态文件各约 31.23 GiB，包含 1,548 个数组。最终文件逐字节相同，数组全部为有限值，Adam 状态非零；恢复后的 9 批、72 行生成数据、随机状态、概率、mask 和参数变化记录一致。两份四题评估的实际 token、解码文本和重新评分也一致，正确题数为 1/4。这验证了指定配置下的保存和恢复，不用于判断学习效果。

整个示例约运行 20.5 分钟，包含编译、保存、两次评估和大文件检查。运行 `examples/e2b_grpo_recovery.sh` 可以完成训练、保存、继续训练和评估，并在指定输出目录生成状态文件和比较结果。

历史引擎已有特定配置的保存和继续训练结果，但当前代码的完整引擎比较、异常退出和资源回收仍需继续测试。真正并行的训练与生成还需要额外处理队列、策略滞后和恢复状态。

## E4B 和 12B LoRA

E4B 使用冻结 embedding、BF16 计算和 FP32 状态，B8/G8/P512/N1024/micro4，每批数据用于两个训练步。关闭重计算时编译内存超出容量，开启后完成四步训练、保存和重载评估：1,909 个状态数组均为有限值，重载后的 32 条文本、长度和评分一致。这个实验没有比较恢复后继续训练的轨迹，也没有保存用于比较的实际 token 数组。

另外进行了三次训练，每次使用不同的随机种子、训练 30 步。初始准确率为 92.0%，三次末步分别为 91.8%、92.4%、92.4%，平均 92.2%。0.2 个百分点的平均变化还不足以说明稳定改善。这三次训练关闭了保存，因此没有对应的三个末步 checkpoint。

12B LoRA 的 CPU 数学测试使用固定 B2/T8、rank 8、alpha 16。双方 FP32 时，338/368 个适配器梯度数组未达到相对 L2 误差低于 `1e-4` 的要求；双方提升到 FP64 后，368 个数组全部通过，最大误差约 `5.91e-13`。JAX FP32 与 Transformers FP64 参考比较时也全部低于 `1e-4`。这说明参考实现本身的 FP32 误差同样需要检查；真实 12B 的 TPU 容量、训练和恢复仍未完成验证。

## 没有采用的优化

| 尝试 | 实测结果 | 当前处理 |
|---|---|---|
| FSDP 参数打包与局部还原 | 小模型通过，真实 E2B 梯度相对 L2 误差约 0.03666 | 超出误差要求，继续分析计算图差异 |
| 分块 TopK | B32、词表 262144、k=50 时，内置 TopK 约 0.9058 ms，最佳分块约 1.6419 ms；B128 也慢约 2.25% | 保留内置 TopK |
| EOS 后压缩活跃请求 | 96 题的执行槽位从 93,312 降到 51,188，但 49/96 条回答改变 | 尚不作为等价优化使用 |

FSDP 对照还发现，启用 donation 和 Adam 后的真实训练图，其首步 loss 与独立梯度图没有满足原定误差要求。即使单独的梯度检查通过，也仍需验证实际计时和训练使用的图。

这些未采用的结果同样提供了信息：减少槽位不一定保持生成行为，手写 kernel 不一定比内置算子快，独立计算通过也不保证完整训练图一致。后续工作应围绕这些具体原因继续，而不是重复同配置实验或仅凭局部速度宣布优化成功。
