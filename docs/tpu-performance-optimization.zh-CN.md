# TPU 极致性能优化：以高效框架为起点，充分利用硬件能力

[English](tpu-performance-optimization.md) | **简体中文**

TPU 极致性能优化需要一个好的框架作为起点，并结合硬件本身的能力，继续向下压榨性能。框架层面要把完整任务组织得高效，硬件层面则要深入实际的数据路径和指令执行，寻找现有实现没有充分利用的空间。这两部分共同决定端到端表现。

在 Gemma 4 E2B-it 的同步 GRPO 实验中，我比较了本项目和调优后的 Tunix，分别使用各自的原生 rollout，以及接入同一个 tpu-inference 引擎时的完整迭代耗时。在 B8/N1024 和 B16/N2048 两组配置下，本项目使用原生 rollout 时耗时最低。双方都使用原生 rollout 时，本项目吞吐为 Tunix 的 **1.69–1.79 倍**；双方接入同一个引擎时为 **1.03–1.14 倍**。

下表单位为**秒/完整迭代，越小越快**。每格两个数字来自两个独立进程，每个进程完成 12 次参数更新，取第 7–12 次迭代耗时的中位数。斜杠分隔两次运行结果，不表示训练与推理各自的耗时。

| 配置 | 本项目＋原生 rollout | Tunix＋原生 rollout | 本项目＋tpu-inference | Tunix＋tpu-inference |
|---|---:|---:|---:|---:|
| B8 / N1024 | **4.095 / 4.098** | 7.177 / 7.350 | 9.754 / 9.623 | 11.084 / 10.825 |
| B16 / N2048 | **15.188 / 15.177** | 25.703 / 25.843 | 25.280 / 25.018 | 26.064 / 25.937 |

两组实验使用同一组四颗 TPU v4，训练和生成轮流使用全部芯片。B 是每批问题数，每题生成 4 条回答；prompt 容量为 512，N 是回答长度上限，分别为 1024 和 2048，microbatch 为 4。每批回答执行一次 GRPO 更新，β=0，开启层重计算；模型采用 BF16 计算，推理权重和 KV 使用 BF16，主参数和 Adam 状态使用 FP32。两边共同可训练参数与 Adam 状态的元素数已经对齐。

实验通过固定完整回答序列保持两边工作量一致，模型仍实际执行生成、概率计算、梯度计算和 Adam 更新。B8、B16 每轮分别包含 11,627 和 28,683 个有效回答 token，包含 EOS、不含 padding。每种生成后端分别按“本项目 → Tunix → Tunix → 本项目”的顺序运行，以检查先后顺序的影响。

计时包含权重准备与等待、生成、文本解码、奖励计算、参数更新和循环内记录，不含初始加载与编译、周期性保存与评估、训练结束后的完整状态检查。表格来自已完成的原始实验；整理后的公开代码尚需完成同配置的 E2B TPU 复跑。

这些结果说明，在已测的同步、固定工作量配置下，框架和生成实现的选择会明显影响完整迭代成本；接入同一个推理引擎后，两者的差距较小。它们支持把高效框架作为继续优化硬件执行的起点，但不能据此判断自然采样时的学习质量，也不能推广为所有 batch size 和生成长度下的排名。

## 一、极致性能优化的目标，是找到更好的TPU硬件执行方案

算子、编译器、计算图都是组织硬件上的指令执行的方式。从硬件执行的角度看，训练/推理的实际操作最终会变成关于数据搬运、计算、同步和通信的指令。深入指令层，可以从本质考虑 TPU 硬件的能力边界，决定数据放在哪里、经过哪些执行单元、何时发起 DMA，以及哪些依赖必须等待。

这样看来，可以把这个目标形式化。设：

- $`D`$ 是固定的硬件与运行条件，包括 TPU 代际、芯片数量、互联拓扑、存储层次和主机环境。
- $`S`$ 是必须满足的计算语义，包括精度、允许的数值误差和输出要求。
- $`X`$ 是输入条件，包括输入范围或分布、shape、batch、初始状态，以及动态任务的请求到达方式。
- $`\mathcal{P}(D,S,X)`$ 是满足上述条件的全部可行执行方案，$`T(p)`$ 是方案 $`p`$ 在固定计时边界和统计方法下的端到端执行成本。

当优化目标是最小化执行时间、且最小值能够取得时，可以把最优方案记为 $`H`$：

```math
H \in \arg\min_{p\in\mathcal{P}(D,S,X)} T(p),
\qquad T^{\star}=T(H).
```

$`H`$ 是最优的指令执行方案，包含各芯片上的指令序列、数据布局、执行调度、通信与同步，也包含必要的主机和设备协作。

这个定义给出了优化的方向：不断减少当前方案与 $`T^{\star}`$ 的差距。这不意味着最优方案唯一、或者已知、或者有限次实验必然能找到它，但我们可以通过实验尽可能接近这个最优方案。如果不能保证最小值被取得，就用 $`\inf_{p\in\mathcal{P}}T(p)`$ 表示理论下界；如果目标换成服务成本或延迟约束下的吞吐，就相应更换目标函数与约束。

高层抽象对这个目标的影响，可以用可表达的方案范围来理解。固定一个框架 $`F`$ 及其允许的扩展方式，它能生成的合法执行方案构成 $`\mathcal{P}_F\subseteq\mathcal{P}`$，于是：

```math
\inf_{p\in\mathcal{P}}T(p)
\;\leq\;
\inf_{p\in\mathcal{P}_F}T(p).
```

如果框架固定了不合适的算子边界、布局或通信方式，就可能排除更快的执行方案。每一层抽象都值得检查这些约束。不过，这个不等式允许取等号：抽象带来表达上的约束，不等于每一层都必然增加运行时间。

我们在使用编译器时，认为编译器可以给出一个可行的方案，而更优的方案则需要手写算子来得到。那么更进一步的，其实手写算子也是给出一个能够用算子表达的可行方案，从指令的视角进一步考虑优化问题，通过指令层级的优化可以更底层更本质的向最优方案接近。

下面给出一个用指令来考虑优化的例子，在独立的 `sampling-tpuasm-dev` 项目中，我借助 tpuasm 考虑对采样进行优化。在四颗 TPU v4 上的 BF16 采样实验中，我为 64 个请求从 131072 个词中各采样一个 token，输入已在 HBM。检查这次原生 JAX 的 Megacore 编译产物时，发现同一芯片上的两个 TensorCore 各自读取完整的 4 MiB 数据，做了重复计算。我先用 Pallas 明确两个 TensorCore 各处理 32 个请求、调用硬件 PRNG，再结合预取与 tpuasm IAR 改写优化数据访问。朴素 Pallas 把跨芯片合并放在 kernel 外，优化版则把它融合进来，因此不能直接比较单个 kernel。对齐完整采样区间、TensorCore 分工和硬件随机流后，LCC 中位数从 78029 降到 42095.5，设备加速约 1.85 倍；主机同步调用从 328.11 降到 300.39 微秒，耗时减少约 8.45%。指令层级的优化给出了更极致、更准确的优化方向。

尽可能利用硬件能力、不设限制，是实现思路不预先停在框架、Pallas 或编译器当前接口的边界，继续研究 lowering、tpuasm 机器指令和执行时序，尽可能利用 TPU 硬件。

## 二、既然最终要优化硬件执行，为什么还需要训练/推理框架？

既然最终要优化硬件执行，为什么还需要框架？我觉得是因为完整系统需要一个高效、可继续优化的起点。

如果是单个芯片上的简单、固定计算，完全可以直接从 TPU 指令出发，通过大量实验逐渐接近硬件最优执行 $`H`$。

但是 LLM 的训练/推理，并不是只有一颗芯片，一个完整的分布式 LLM workload，需要同时考虑计算与数据流、内存布局、模型分片、跨芯片通信，以及编译期和运行时的执行调度。 这些决策之间又存在强烈的相互影响，把搜索范围扩展到指令层，理论上可以探索更多方案，但完整系统的组合空间非常大。在多机、多芯片上，一次布局变化会影响通信和内存占用；一次融合会影响编译器的预取与调度；动态请求还会改变 batch、KV cache 和执行顺序。即使能够直接编写指令，也需要先组织好计算与数据流，确定从哪里开始优化。

LLM 的训练和推理包含大量可复用的结构，例如矩阵乘、attention、归一化和分布式通信。训练还需要梯度、优化器和状态恢复，推理还需要 KV cache 和生成调度。这些基础流程已有成熟的表达方式，可以先复用，再针对模型、shape、精度和目标硬件做更细的优化。每次从机器指令重建完整流程，会把大量精力花在重复工作上。

这就是好的框架作为对指令进一步进行优化的起点的价值。它先提供完整、正确、具有竞争力的执行方案，让后续优化有可运行的基线、有可比较的成本，也有可以替换的具体位置。前面约 1.8 倍的固定工作量成本差，说明在已测配置下，选择我的框架作为起点已经能少付一部分执行成本。这个优势值得保留，但它来自现有实现和配置的组合，不能直接把全部差距归因于某一个调度策略或某一个 kernel。

调度本身也必须进入优化目标。早期标准 GRPO 流程中，我发现生成与更新程序因为驻留空间不足而反复装载：profile 中一次更新约有 111 ms 用于装载，生成另有约 43 ms。调整编译设置后，更新程序代码从约 0.73 GB 缩小到 0.18 GB，两个程序能够同时驻留。虽然设备上的更新计算多了约 4 ms，完整流程仍然受益。结合上一轮的打包收集改动，平均训练步从 2.981 降到 2.748 秒，耗时降低约 7.8%；50 步训练的 1600 条回答、非计时指标、对应评估以及续训和重载检查保持一致。

框架的价值，不是替我们决定最优执行方式，而是让我们从一个高质量的起点出发，更有效地探索最优执行方式。

好的框架应该“形神兼备”。

我认为，一个真正好的 TPU 框架需要同时具备两个方面的能力。

* 第一，是组织完整 workload 的能力。

    它应该提供良好的计算组织、数据流、分布式执行和调度能力。

    尤其是调度，既包括芯片内部计算和 DMA 的重叠，也包括多芯片通信、流水线以及运行时动态 batching 等问题。

    这相当于训练和推理系统的“形”：让完整系统能够正确、有序且高效地运行。

* 第二，是充分利用 TPU 硬件的能力。

    框架应该暴露 TPU 硬件支持的各种操作，让开发者能够控制关键的 layout、内存搬运、流水线和底层执行方式。

    当框架默认的实现不够好时，我们应该能够替换它。当某种有价值的硬件能力尚未得到支持时，应该有合理的扩展路径。

    它还应该提供足够的性能可观测性，让我们看到 HLO、底层 tpuasm 指令、数据搬运以及真实硬件周期，而不仅仅是最终的耗时数字。

    这相当于性能优化的“神”：让训练/推理能不受框架、计算、通信等各方面原理等层面的限制，只是以考虑指令本身的方式尽可能优化。

## 三、Agent 加快探索，我的 TPU 知识决定方向与反馈

Agent 能帮助我阅读代码、实现候选、组织实验和比较编译结果，使我有能力尝试更多方案，也更快地深入到 Pallas 以下的编译与指令层。实验能力扩大之后，选择哪些问题值得做、怎样解释结果，就更加重要。

只给“做 profile、调参数、继续加速”这样的通用要求，并不能保证探索会进入最有价值的底层路径。我需要把 TPU 的存储层次、指令依赖、DMA 和 ICI 通信机制转成具体、可检验的假设，再让 Agent 实现和验证。

我判断 agent 要做的和已经做了的方向对不对。在早期接入tpu-inference，并测试训练两芯、推理两芯的 tpu-inference 的接入方案时，权重同步经过主机耗时41.529 秒。我把优化方向定为共同运行时内的 ICI 直传，并检查实际通信路径，一开始这样优化反而更慢，进一步分析发现，分块写入触发了反复的整参数布局转换。改为保留原行布局、分块传输后，同一固定权重的完整同步时间下降到 3.345 秒。

我还要判断agent给出的结果真不真。在我把 PLE 块也并进融合 kernel，kernel这部分变快了，之后把这个fused kernel也对应修改，却发现完整一步训练的时间反而变慢了，每个 decode 步从 2.36 变成 2.43 毫秒。agent 一开始把它解释成波动。我觉得不对：TPU 是静态调度的，同一份程序、只计算的延迟周期数每次都一样，DMA和通信可能有一定波动，但也在某个范围内。差异能在独立进程中稳定复现，而且方向一致，值得先检查两边的程序和执行条件。然后发现差别在循环。历史kernel里的实现用的是 scan，循环次数编译时就知道；完整一步generation时用的是 while 循环，要等所有回答都写完才停，次数编译时不知道。XLA 的内存规划估算收益时，会把这种次数未知的循环当作跑 5 次。我让agent把这个设置用不同的数值扫了一遍，一步步发现根因在于 XLA 内存规划器（MSA）对未知次数的 while 循环默认估算执行 5 次。在这个估算下，MSA 触发了内部的一个 OOM Cache Bug，直接放弃了提前预取，导致矩阵乘法被迫原地等待 HBM DMA。我通过修改 XLA 的 bug，找回了更优的预取，时间立刻降到了 2.16 毫秒。

所以对于agent给出的结果，一方面要用 skill 设立一些检查，另一方面具体到和结论相关的这些部分，还是需要靠我来直接进行判断和指挥。
